# План preflight: полный GRPO на 1× RTX 4070 8 GB, затем на 2× RTX 4070 по LAN

**Цель файла:** не получить научные результаты на ноутбуках, а заранее доказать работоспособность всей цепочки GRPO перед переносом того же репозитория/commit на 2× RTX 5090 или 2× H100.

Целевая цепочка без speculative decoding:

```text
GSM8K batch
  -> текущая Qwen policy генерирует G trajectories
  -> rule-based reward
  -> group-relative advantages
  -> GRPO policy loss
  -> обычный PyTorch backward
  -> optimizer.step()
  -> новые веса policy
  -> weight sync в rollout engine
  -> следующий batch генерируется уже новой policy
```

На ноутбуках **SPEC_METHOD=none**. EAGLE/DFlash/DSpark подключаются только после того, как этот файл пройден до конца.

---

## 0. Что считаем успехом

### Успех на одном ноутбуке

Мы должны доказать, что на `Qwen/Qwen3-0.6B` реально происходят:

1. загрузка GSM8K;
2. rollout нескольких ответов на prompt;
3. rule reward;
4. GRPO advantages;
5. actor policy loss;
6. `backward`;
7. ненулевой `actor/grad_norm` хотя бы на одном шаге;
8. `optimizer.step()`;
9. изменение policy;
10. weight sync в vLLM;
11. второй rollout после sync;
12. сохранение checkpoint и хотя бы один успешный resume.

Это **functional full-GRPO run**, а не benchmark.

### Успех на двух ноутбуках

Всё выше плюс:

1. Ray видит два узла;
2. на каждом узле видна ровно одна 4070;
3. FSDP2 работает с `world_size=2`;
4. forward/backward не зависает на NCCL collectives;
5. `trainer.nnodes=2`, `trainer.n_gpus_per_node=1`;
6. vLLM остаётся с `tensor_model_parallel_size=1`;
7. проходит минимум два live training steps;
8. проходит более длинный 10–20 step run;
9. checkpoint создаётся и может быть продолжен.

# Часть I. Один ноутбук: 1× RTX 4070 8 GB + 64 GB RAM

## 1. Ограничение железа

Официальный GSM8K quickstart verl сейчас ориентируется на GPU минимум с ~24 GB HBM. Поэтому 8 GB RTX 4070 — ниже официального комфортного профиля.

Именно поэтому здесь:

- `Qwen/Qwen3-0.6B`, а не Qwen3-4B;
- aggressive CPU offload;
- `ppo_micro_batch_size_per_gpu=1`;
- короткие ответы;
- маленький train batch;
- gradient checkpointing;
- vLLM TP=1;
- никаких draft heads.

Qwen3-0.6B имеет файл весов примерно 1.5 GB, поэтому это намного реалистичнее Qwen3-4B для 8 GB VRAM.

**Важно:** нам не нужна хорошая скорость. Если training step занимает минуты — это нормально. Нам нужна причинно правильная цепочка.

### Почему offload включён

На 8 GB VRAM главная задача — уменьшить одновременно живущие на GPU:

- actor parameters;
- gradients;
- optimizer state;
- reference model;
- vLLM/KV-cache.

FSDP2/verl offload меняет скорость на память. На ноутбуке это приемлемо.

## На этом этапе НЕ требовать

- хорошего reward;
- ненулевого gradient на конкретном единственном prompt;
- хорошей скорости.

Если обе trajectories получили одинаковый reward, group-relative signal может быть нулевым.

## Требовать

- rollout завершился;
- reward был посчитан;
- код дошёл до actor update;
- процесс не упал по OOM;
- training step завершился.

# 12. Если на 8 GB OOM: изменять по одному параметру

Нельзя одновременно менять пять вещей.

## OOM во время rollout

Порядок:

1. `MAX_RESPONSE_LENGTH: 64 -> 32`;
2. `ROLLOUT_N: 2` оставить;
3. уменьшить `rollout.gpu_memory_utilization`;
4. уменьшить `max_num_batched_tokens`;
5. убедиться, что actor/ref offload действительно включён.

Если vLLM, наоборот, пишет, что ему недостаточно памяти даже для model/KV cache, `gpu_memory_utilization` может понадобиться немного **увеличить**, а не уменьшить. Важно читать конкретную ошибку.

## OOM во время actor update/backward

Проверить:

```text
ppo_micro_batch_size_per_gpu=1
gradient_checkpointing=True
actor param_offload=True
actor optimizer_offload=True
```

Затем уменьшать:

```text
MAX_RESPONSE_LENGTH
ppo_max_token_len_per_gpu
```

## OOM при reference logprob
Проверить:

```text
ref.fsdp_config.param_offload=True
ref.log_prob_micro_batch_size_per_gpu=1
```

```bash
TRAIN_FILE=$HOME/grpo_preflight/data/gsm8k/train.parquet \
VAL_FILE=$HOME/grpo_preflight/data/gsm8k/test.parquet \
bash scripts/run_live_grpo.sh
```

`G=4` предпочтительнее `G=2`, потому что выше вероятность reward diversity внутри группы.

### Обязательный причинный порядок

```text
rollout(step 0)
  <
reward / advantages
  <
update_actor(step 0)
  <
weight sync(step 0)
  <
rollout(step 1)
```

### Обязательные признаки

- есть два distinct training steps;
- generation есть на обоих;
- `actor/grad_norm > 0` хотя бы на одном;
- есть actor update;
- есть weight synchronization;
- второй rollout происходит после sync.

Если все rewards внутри всех групп одинаковые и `grad_norm≈0`, сначала менять seed/prompts/G, а не обвинять backward.


Если на ноутбуках нет InfiniBand, а NCCL пытается его использовать/долго ищет:

```bash
export NCCL_IB_DISABLE=1
```

Не добавлять такие переменные «на всякий случай» до появления соответствующей проблемы.

# 24. Не делать TP=2 через LAN

Для двух ноутбуков:

```text
trainer.nnodes=2
trainer.n_gpus_per_node=1
rollout.tensor_model_parallel_size=1
```

Это принципиально.

Сеть проверяет:

- Ray;
- FSDP2;
- NCCL.

Но мы **не хотим** одновременно проверять cross-node tensor parallel vLLM.

Официальный verl multi-node пример использует именно 2 nodes × 1 GPU и vLLM TP=1.

# 27. Запуск через существующий Ray cluster

На multi-node лучше ориентироваться на официальный verl flow:

1. head запускает Ray;2. worker присоединяется;
3. `ray status` показывает два nodes;
4. training job подаётся с head;
5. Ray запускает workers на обеих машинах.

Если custom launcher пока автоматически создаёт только local Ray, не пытаться «обмануть» его.

Сначала вынести точную команду из `DRY_RUN`, затем подать её через `ray job submit` по официальному manual multi-node pattern.

Официальный pattern:

```bash
ray job submit \
  --address="http://127.0.0.1:8265" \
  -- \
  python3 -m verl.trainer.main_ppo \
  trainer.n_gpus_per_node=1 \
  trainer.nnodes=2 \
  ...
```

Для pinned coursework environment нужно также сохранить тот же `uv` Python для driver/workers, как это уже делает `run_live_grpo.sh`.

# 30. Functional distributed GRPO

После успешных 2 steps:


# 31. Что сравнивать между 1×4070 и 2×4070

**Не сравнивать speed.**

LAN делает performance comparison почти бессмысленным для будущих H100/5090.

Сравнивать только correctness:

| Проверка | 1×4070 | 2×4070 |
|---|---|---|
| GSM8K load | ✓ | ✓ |
| rollout | ✓ | ✓ |
| reward | ✓ | ✓ |
| GRPO advantages | ✓ | ✓ |
| policy loss | ✓ | ✓ |
| backward | ✓ | ✓ |
| grad norm | ✓ | ✓ |
| optimizer step | ✓ | ✓ |
| weight sync | ✓ | ✓ |
| second rollout | ✓ | ✓ |
| FSDP2 world size > 1 | — | ✓ |
| NCCL communication | — | ✓ |
| Ray multi-node | — | ✓ |
| checkpoint | ✓ | ✓ |
| resume | ✓ | ✓ |

# 32. Что НЕ нужно доказывать на ноутбуках

Не использовать ноутбучные результаты для утверждений о:

- acceptance EAGLE/DFlash/DSpark;
- speedup speculative decoding;
- throughput H100/5090;
- оптимальном `G`;
- оптимальном KL coefficient;
- финальном GSM8K quality;
- memory profile Qwen3-4B.

Ноутбуки отвечают только на вопрос:

> «правильно ли собран training system и проходит ли полный live GRPO cycle?»

# 34. Перенос на 2×5090 / 2×H100

После preflight не писать новую реализацию.

Меняется профиль:

```text
MODEL_PATH:
Qwen/Qwen3-0.6B
    ->
Qwen/Qwen3-4B
```

и resource config:

```text
1/2 laptop 4070
    ->
2 local datacenter/desktop GPUs
```

Возвращаются:

```text
trainer.nnodes=1
trainer.n_gpus_per_node=2
rollout.tensor_model_parallel_size=2
```

После подтверждения памяти можно отключать laptop-only offloads:

```text
actor param_offload=False
actor optimizer_offload=False
```

Reference offload оставить/изменить только после memory smoke.

Сначала на 5090/H100 снова:

```text
SPEC_METHOD=none
2-step AR GRPO smoke
```

И только после него:

```text
EAGLE-3
DFlash
DSpark
```

То есть expensive server не является местом, где мы впервые узнаём, работает ли GRPO.

# 36. Troubleshooting decision tree

```text
command не строится
  -> launcher/Hydra/config problem

imports не работают
  -> environment problem

CUDA model inference не работает
  -> driver/CUDA/PyTorch problem

GSM8K не читается
  -> data problem

rollout OOM
  -> vLLM/KV/model memory problem

rollout проходит, backward OOM
  -> actor/activation/optimizer memory problem

reward есть, grad=0
  -> проверить group reward variance

grad != 0, но второй rollout старой policy
  -> weight-sync problem

1 GPU работает, NCCL smoke не работает
  -> network/NCCL problem

NCCL smoke работает, Ray не видит worker
  -> Ray/firewall/address problem

Ray видит 2 GPU, distributed backward висит
  -> FSDP2/NCCL/resource placement problem
```
